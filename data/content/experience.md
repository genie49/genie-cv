AI Productivity and Agent 팀은 AI로 사내 구성원의 업무 효율을 높이는 팀입니다. 당근은 데이터를 바탕으로 의사결정하는 조직인 만큼, 데이터 분석가가 아니어도 모든 구성원이 필요할 때 직접 데이터를 분석할 수 있도록 돕고자 했습니다. 사내 데이터 분석 에이전트는 이를 위해 진행한 팀의 프로젝트 중 하나입니다. 각 팀이 제품 코드와 자산을 자율적으로 관리하고 있어, 필요한 지식이 저장된 위치와 운영 방식이 서로 달랐습니다. 따라서 다양한 자산 관리 방식을 수용하고 각 팀의 시스템에 연결할 수 있는 구조가 필요했습니다.

## 당근 — 프롬프트 캐싱 최적화

입사 초기에는 사내 데이터 분석 에이전트의 프롬프트 캐시가 반복해서 다시 작성되는 문제를 다뤘습니다. 질문별 동적 정보가 고정 지식과 섞여 있었고, 실행 로그에서는 비동기 로딩에 따라 스킬 조립 순서도 달라지는 것을 확인했습니다. 고정 정보와 질문별 정보를 분리하고 조립 순서를 고정했으며, 캐시 쓰기 토큰과 비용 계측을 보강했습니다.

## 당근 — 에이전트 평가 하네스 구축

에이전트는 같은 질문에도 분석 기준과 실행 과정이 달라질 수 있어, 개별 답변이나 일부 실행 로그만으로는 변경 효과를 판단하기 어려웠습니다. 프롬프트나 도구의 수정이 전체 분석의 품질과 효율에 미치는 영향을 확인하려면, 같은 조건에서 실행을 비교하고 결과의 원인까지 살펴볼 수 있어야 했습니다. 이에 실제 사용자 질문을 반복 실행하는 평가 하네스를 구축했습니다. 답변 품질과 응답 시간, 토큰 사용량을 측정하고 세부 행동과 단계별 소요 시간을 기록해, 문제를 수정한 뒤 같은 기준으로 다시 평가할 수 있도록 했습니다.

기록을 살펴보니 에이전트가 방대한 데이터셋에서 필요한 데이터와 조회 방법을 찾지 못해 탐색을 반복하고, 같은 질문에도 분석 기준이 달라지는 문제가 있었습니다. 이로 인한 응답 지연과 품질 저하를 다음 개선 과제로 삼았습니다.

## 당근 — 에이전트 실험/개발/개선 환경 구축

평가에서 드러난 반복 탐색과 분석 기준의 차이를 줄이기 위해, 분석에 필요한 도메인 지식을 에이전트에 연결하는 실험을 진행했습니다. 당근알바 일부 질문과 데이터로 진행한 PoC에서 이 지식을 활용하자, 기존 데이터 에이전트 대비 **답변 평가 통과율이 60%에서 78%로 18%p 높아졌고, 응답 시간 중앙값은 49.9초에서 24.9초로 약 50% 줄었습니다.** 이 결과는 팀의 가설을 확인하고 제품화에 착수하는 의사결정의 근거가 되었습니다.

이러한 실험을 팀 전체가 이어가려면 지식 관리와 에이전트 실행을 공통 기반으로 제공할 필요가 있었습니다. 엔지니어와 비엔지니어 출신 구성원이 함께하는 팀에서 각자가 DB와 실행 환경까지 구성해야 하면, 자신의 전문성을 활용한 실험에 집중하기 어렵다고 판단했습니다.

이를 위해 DB 인프라와 연결 계층을 구축하고, 지식 저장/조회와 에이전트 실행, 트레이스/평가 연동을 공통 패키지로 묶었습니다. 동료들은 하위 구현을 직접 다루지 않고 Agent 같은 상위 객체를 가져와, 업무에 맞는 모델과 도구/스킬을 구성하며 실험할 수 있도록 했습니다.

구축한 지식이 실제 업무의 변화에 맞춰 계속 갱신되도록, 런타임 트레이스와 지식 조회 기록, 제품의 코드 변경과 업무 대화를 주기적으로 수집하는 워커를 구현했습니다. 워커가 이 자료를 바탕으로 기존 지식의 누락과 변경 사항을 찾아 수정하고 보완하도록 했습니다. 갱신된 지식이 이후 에이전트 실행에 활용되고, 그 실행 기록이 다시 다음 갱신의 근거가 되는 순환 구조로 구성했습니다.

## 아이머스 — 캠페인 자동화 에이전트 개발

사용자가 제공한 웹사이트와 인스타그램, 유튜브, 틱톡 계정의 원본 자료를 해석해, AI가 사업자와 브랜드를 이해하고 기획에 활용할 수 있는 데이터로 가공했습니다. 이를 바탕으로 에이전트가 스스로 진행할 작업과 사용자 확인이 필요한 시점을 구분하고, 캠페인 기획부터 인플루언서 매칭, 콘텐츠 가이드와 계약 관리까지 이어지는 흐름을 구성했습니다.

업무가 늘면서 한 에이전트에 도구와 실행 기록이 쌓여 판단 정확도가 떨어졌고, 프롬프트 수정만으로는 한계가 있었습니다. 사용자 의도와 작업 배분을 맡는 Supervisor 아래에 업무별 서브에이전트를 두었습니다. 실행과 컨텍스트 관리는 공통화하고, 업무별 절차/지식/전용 도구는 Skill로 묶었습니다. 각 에이전트는 필요한 Skill만 읽고 도구의 데이터 수정 범위도 업무별로 제한했습니다.

Supervisor는 Tool Calling으로 서브에이전트를 호출해 업무별 라우팅 분기를 줄였습니다. 서브에이전트는 독립된 컨텍스트에서 실행하고 최종 결과만 반환하도록 해, Supervisor의 컨텍스트를 **약 80~120k에서 15~25k 토큰으로 줄였습니다.** 이에 따라 캠페인을 진행하는 **에이전트 루프의 실행 비용도 약 30% 절감했습니다.** 각 서브에이전트가 담당 업무에 필요한 지식과 도구에 집중하도록 구성하면서, 에이전트가 기획하는 캠페인의 품질도 눈에 띄게 향상됐습니다.

## 아이머스 — 실시간 응답과 장애 복구를 위한 백엔드 구축

사용자 연결과 에이전트 실행을 별도 서비스로 나누려면, 두 서비스가 비동기로 작업과 결과를 주고받을 수 있어야 했습니다. 기존 GCP 환경을 활용하고 메시징 인프라의 운영 부담을 줄이기 위해 Google Pub/Sub을 선택했습니다. 처음 사용하는 기술이었기에 공식 문서로 발행/구독의 기본 개념을 빠르게 익히고, 이를 바탕으로 시스템의 메시지 흐름을 설계했습니다. 이후 필요한 기능을 직접 구현하고 테스트하면서 실제 서비스에 적용하는 방식으로 숙달했습니다.

사용자가 접속을 종료해도 AI 작업은 계속 진행되어야 했고, 실행 부하가 사용자 연결에 영향을 주지 않도록 해야 했습니다. 이에 에이전트 실행에 집중하는 Workflow 서비스와 사용자 클라이언트와의 통신을 중계하는 Chat 서비스로 역할을 나눴습니다. Workflow는 에이전트를 구동하며 응답 청크, 도구 실행 상태, 데이터 변경 등 중간 산출물을 Pub/Sub으로 계속 발행하고, Chat은 이를 받아 WebSocket으로 클라이언트에 전달하도록 했습니다. 에이전트가 사용자의 접속 상태와 관계없이 실행되는 동안, 접속 중인 사용자는 진행 상황을 실시간으로 확인할 수 있도록 구성했습니다.

사용자 연결 수와 AI 작업량에 필요한 자원이 달라 두 서비스를 각각 수평 확장할 수 있도록 구성했습니다. 인스턴스가 늘어나도 결과가 올바른 사용자에게 전달되도록 Redis에서 사용자별 Chat 연결 위치를 관리하고, Pub/Sub의 메시지 속성 필터링으로 해당 인스턴스에 라우팅했습니다. 새 인스턴스도 연결 정보를 등록하면 메시지 전달에 참여하도록 했습니다.

장애가 발생한 인스턴스는 heartbeat 만료를 기준으로 전달 대상에서 제외하고, Workflow가 재시작돼도 Chat의 연결은 유지하도록 했습니다. 실행 중인 작업도 이어갈 수 있도록 각 Workflow Pod가 담당 세션의 heartbeat를 Redis에 주기적으로 기록하게 했습니다. 갱신이 끊겨 고아 세션 기준에 도달하면 다른 Pod가 세션을 인계받아 실행을 이어가도록 구현했습니다.

## 아이머스 — 트렌드 탐지 시스템 개발

캠페인을 기획하는 에이전트가 기존 지식에만 의존하면 아이디어의 범위에 한계가 있어, 시의성 있는 뉴스와 도메인 지식을 제공하고자 했습니다. 트렌드를 탐지할 방법에 대해 구성원들이 다양한 아이디어를 제안했지만, 어느 접근이 효과적인지 확신할 근거가 없어 방향을 결정하지 못하고 있었습니다.

저는 각 아이디어를 먼저 구현하고 실험해 판단에 필요한 데이터를 만들자고 제안했습니다. 구현과 평가를 반복하고 그 결과를 다음 실험에 반영하는 autoresearch 방식을 적용했습니다. 실제 뉴스 사건을 직접 검수해 공통 평가셋을 만들고, 1차 탐지에서 놓친 사건은 후속 LLM도 검토할 수 없다는 점에서 재현율을 우선 지표로 정했습니다. 도입 여부를 판단할 수 있도록 목표 재현율도 사전에 설정했습니다.

AI를 활용해 접근 방식과 파라미터를 바꿔가며 실험하고, 조건별 지표와 실패 사례를 기록했습니다. 실험에서 얻은 데이터와 배운 점으로 다음 가설을 정하고 검증을 이어가며, **하루 만에 목표 재현율을 상회하는 방식을 찾았습니다.** 실험 결과와 비교 데이터를 팀에 공유했고, 이를 근거로 도입할 방식을 원활하게 결정할 수 있었습니다.

## 아이머스 — 콘텐츠 생성과 검토 과정 자동화

탐지한 트렌드를 실제 콘텐츠 제작에 활용하도록 생성 파이프라인으로 확장하면서, 콘텐츠 담당자와 협업했습니다. LLM이 만든 내용을 그대로 다음 단계에 넘기기에는 신뢰성이 부족했고, 콘텐츠의 적절성을 판단하는 담당자의 직관이 필요했습니다. 담당자가 모든 단계를 직접 처리하는 부담을 줄이기 위해 판단이 필요한 지점에 승인 단계를 두고, 통과하면 후속 작업이 자동으로 진행되도록 했습니다.

담당자가 한 페이지에서 결과를 검토하고 승인과 피드백을 입력하도록 구현했습니다. 다음 처리를 직접 실행하는 부담을 줄이고, 피드백은 생성 파이프라인 개선에 반영했습니다. 승인 단계는 사람의 판단이 계속 필요한 곳과 신뢰성 향상 후 자동화할 수 있는 곳을 구분해, 추후 전환이 쉽도록 설계했습니다.

다만 재생할 때마다 음성을 합성하면 학생이 발음을 반복해서 들을 때마다 대기 시간과 API 비용이 발생했습니다. 브라우저의 IndexedDB에서 음성을 먼저 찾고, 없으면 S3에 저장된 음성을 조회한 뒤 두 곳 모두 없는 경우에만 합성해 저장하도록 구성했습니다. 캐시 키는 데이터 행 ID 대신 텍스트/언어/음성 유형으로 정의해, 서로 다른 단어장에 같은 단어가 있어도 기존 음성을 재사용하도록 했습니다. 이를 통해 음성 지원 범위를 넓히면서 반복 학습에 따른 중복 합성을 줄였습니다.

## 꿈담길 / 보카톡톡 — 선생님과의 협업을 통한 학습 관리와 콘텐츠 제작 개선

학생들이 서비스를 꾸준히 활용하려면 수업을 준비하고 학습을 관리하는 선생님의 불편도 해결해야 했습니다. 선생님들과 직접 인터뷰하며 필요한 기능과 사용 중 불편한 점을 듣고, 대표님과 함께 사업 미팅에도 참여해 기관마다 서비스를 어떻게 활용하려는지 파악했습니다. 이 과정에서 학생별 학습 기록을 일일이 확인하는 부담과 학습 콘텐츠를 직접 제작하는 어려움을 확인했습니다.

선생님이 학생들의 학습 내용과 진행 상황을 한눈에 볼 수 있도록 관리 화면을 개선했습니다. 모든 학생의 기록을 같은 비중으로 살펴보기보다 학습 기록에서 이상 징후가 있는 학생을 바로 파악할 수 있도록 해, 도움이 필요한 학생에게 집중할 수 있게 했습니다. 콘텐츠 제작 부담을 줄이기 위해서는 LLM을 이용한 학습 콘텐츠 생성 자동화를 추가했습니다.

현장에서 들은 불편을 빠르게 기능으로 개선하면서 선생님들로부터 긍정적인 피드백을 받았습니다. 이러한 개선은 서비스가 **학원/지역아동센터/학교 등 10여 곳에 납품되고, 학교 수행평가에도 활용되는 성과**로 이어지는 데 기여했습니다.
