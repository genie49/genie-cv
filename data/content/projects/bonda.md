# Bonda — 문화재 발굴 보고서 AI 검색 시스템

문화재청 발굴조사보고서와 UNESCO 세계유산 보존현황보고서(SOC)를 AI로 검색하는 RAG 시스템. PDF에서 텍스트와 이미지를 추출하고, 벡터DB에 저장하여 자연어 시맨틱 검색과 메타데이터 필터링을 제공합니다. LangChain 에이전트가 보고서 검색, 이미지 검색, 고고학 사전 조회, 웹 검색 도구를 상황에 맞게 조합해 답변합니다.

## 프로젝트 개요

한국 문화재 발굴조사보고서는 8,000건가량이 대부분 스캔 PDF로만 제공되어 전문 검색이 불가능합니다. 연구자가 특정 시대·지역·유적 유형의 보고서를 찾으려면 그 PDF들을 일일이 열어봐야 하는 문제가 있었습니다.

Bonda는 이 PDF들을 OCR로 텍스트화하고, 청킹·임베딩·벡터 저장 파이프라인을 거쳐 적재한 뒤, 에이전트가 시맨틱 검색으로 관련 내용을 찾아주는 End-to-End RAG 시스템입니다. UNESCO SOC 보고서도 동일한 파이프라인으로 처리하여, 국내 발굴보고서와 세계유산 보존현황을 하나의 인터페이스에서 검색할 수 있습니다.

## 기술 스택

- **프론트엔드**: Next.js, React, Tailwind CSS, assistant-ui, Drizzle ORM (PostgreSQL), Zustand
- **AI 백엔드**: FastAPI, LangChain, Gemini·Claude 멀티모델, SSE 스트리밍
- **전처리**: PyMuPDF (텍스트 추출), 문서 파싱 VLM (dots.ocr), Vision 모델 (이미지 설명), vLLM 위의 GPU 파드 서빙
- **벡터DB**: Qdrant — 검색 단위별 컬렉션 분리, Named Vector
- **임베딩**: Gemini Embedding, 배치 API
- **인프라**: k3s + Kustomize(자체 운영 클러스터), CloudNativePG, Traefik, Redis, S3, Terraform, GitHub Actions 셀프호스트 러너
- **인증**: Auth.js(Google OAuth) + Redis 세션, 앱 JWT로 AI 백엔드 인증
- **운영**: Grafana·Loki 로그 파이프라인, 백업 CronJob과 deadman 알림, LangSmith 트레이싱

## 주요 기능

### End-to-End RAG 파이프라인

크롤러가 문화재청·UNESCO에서 PDF와 메타데이터를 수집합니다. 텍스트 레이어가 있는 PDF는 빠른 경로로 추출하고, 글자 수가 기준에 못 미치는 스캔 PDF만 OCR로 넘깁니다. 모든 PDF에 OCR을 돌리면 GPU 비용이 불필요하게 커지기 때문에, **비싼 경로를 조건부로만 타도록** 설계한 것이 핵심입니다. 추출된 텍스트는 문맥이 끊기지 않도록 오버랩을 두고 문장 경계에서 청킹한 뒤 임베딩합니다. 보고서 메타데이터와 AI 요약은 별도 컬렉션에 저장해 필터링 검색을 지원합니다.

### OCR 폴백 전략

처음에는 텍스트 추출 전용 OCR을 썼습니다. 텍스트는 뽑혔지만 **보고서 안 이미지의 위치를 알 수 없다는 문제**가 뒤늦게 드러났습니다. 이미지 검색을 만들려면 유물 사진이 몇 페이지 어디에 있는지 알아야 했습니다.

그래서 단순 텍스트 OCR이 아니라 문서 구조 인식(Document Parsing)으로 전환했습니다. 페이지를 의미 단위 블록으로 분류해, 텍스트·표는 마크다운으로 변환하고 이미지 블록은 위치 좌표를 반환합니다. 텍스트 인식 성능이 비슷하다면 **가볍고 기능이 많은 쪽**을 택하는 것이 합리적이었습니다.

이후 대량 인제스션 단계에서 파서를 한 번 더 교체했습니다. 레이아웃은 CPU, 인식은 GPU로 나눠 도는 구조라 CPU가 처리량 상한을 잡고 있었는데, 레이아웃·인식·읽기 순서를 하나의 VLM이 GPU에서 처리하는 모델로 옮기며 그 병목이 사라졌습니다. **마크다운 + 이미지 좌표라는 응답 계약을 먼저 고정해 둔 덕분에**, 파서를 통째로 바꾸면서도 호출하는 파이프라인은 수정하지 않았습니다.

### 대량 인제스션 오케스트레이션

8,000건을 며칠에 걸쳐 적재하는 작업은 단계마다 병목이 다릅니다. 크롤은 상대 서버, 파싱은 GPU, 벡터화는 임베딩 API 한도에 걸립니다. 한 프로세스로 순서대로 돌리면 언제나 한 단계만 일하고 나머지는 놉니다.

크롤·파싱·벡터화를 독립 워커로 분리하고 **Redis 큐로 이어**, 각 워커가 자기 큐만 보도록 만들었습니다. 여기에 "크롤됐지만 아직 적재되지 않은 문서 수"를 세는 **역압 카운터**를 두어 크롤러가 앞서 달리지 못하게 막았습니다. 큐 길이가 아니라 파이프라인 전체에 떠 있는 문서 수를 기준으로 삼은 이유는, 어느 단계에 있든 디스크는 이미 점유되고 있기 때문입니다. 적재가 끝나면 로컬 산출물을 즉시 정리합니다.

파싱은 GPU 파드 여러 대에 **진행 중인 요청이 가장 적은 쪽으로** 분산합니다. 문서마다 페이지 수 편차가 커서 순차 분배로는 금방 기울었기 때문입니다. 반대로 벡터화는 **의도적으로 단일 워커**로 두었습니다. 프로세스를 늘리면 레이트리미터가 분산되어 429가 쏟아지는데, 병렬성을 늘리는 대신 한도 아래로 정확히 페이싱해 재시도 낭비를 없애는 쪽이 실효 처리량이 높았습니다.

중단은 예외가 아니라 기본값이라, 큐 중복 발행 차단·단계별 스킵·크롤 재개 지점 보존·미처리 파일 회수까지 **멱등성을 성능 문제로 다뤘습니다.** 중복 한 건이 곧 GPU 몇 분이기 때문입니다.

### 듀얼 벡터 이미지 검색

보고서에서 잘라낸 이미지를 오브젝트 스토리지에 저장하고, 벡터DB에는 두 종류의 벡터를 함께 둡니다. 하나는 이미지 자체를 임베딩한 벡터, 다른 하나는 Vision 모델이 생성한 텍스트 설명을 임베딩한 벡터입니다.

"토기 사진 보여줘"라는 텍스트 검색은 설명 벡터로, "이거랑 비슷한 거 찾아줘"라는 유사 이미지 검색은 이미지 벡터로 처리합니다. 같은 포인트에 두 관점이 공존하니 별도 컬렉션이나 인덱스가 필요 없습니다.

### 지도 기반 공간 검색

발굴보고서는 본질적으로 장소에 묶인 데이터라, 연구자의 실제 질문도 "이 일대에서 발굴된 것"에 가깝습니다. 보고서를 지도에 올리고, 화면 영역이나 사용자가 그린 폴리곤을 그대로 검색 필터로 받도록 만들었습니다.

에이전트는 **지도 상태를 도구로 읽고, 지도를 직접 조작합니다.** 서버가 브라우저 상태를 알 수 없으므로 필요할 때만 실행을 멈추고 프론트엔드에 현재 스냅샷을 요청해 재개하는 구조이며, 뷰 이동·핀·영역·리스트 생성도 같은 통로로 처리합니다. 서버는 액션을 서술하고 실제 실행은 클라이언트가 하기 때문에 판단과 화면 변화 사이에 지연이 없습니다.

초기에는 변경 액션마다 사용자 승인 카드를 뒀지만, 승인률이 도구 실패율보다도 낮고 멀티스텝 작업의 마찰만 키운다는 것이 드러나 **되돌릴 수 있는 액션에서는 승인 게이트를 제거**했습니다. 대신 실패 응답을 표준 엔벨로프로 통일하고 관련 상태 힌트를 함께 실어, 에이전트가 스스로 보완하거나 사용자에게 정확한 질문을 하도록 만들었습니다.

### 멀티모델 AI 에이전트

에이전트가 보고서 시맨틱 검색, 이미지 검색, 고고학 용어 사전, 웹 검색, 지도 조회·조작 도구를 상황에 맞게 조합합니다. 어떤 도구를 어떤 순서로 쓸지 사람이 정하지 않고 에이전트가 질문을 분석해 판단합니다.

연구자에게는 출처가 필수라, 검색 결과에 보고서명과 페이지 범위가 따라붙고 프론트엔드에서 클릭 가능한 링크로 렌더링됩니다. 이미지 검색 결과를 채팅 입력창에 드래그해 다음 질문의 참조로 쓸 수 있어, **검색 → 확인 → 좁히기 → 재검색** 루프가 자연스럽게 이어집니다.

한 API가 불안정했던 시기가 있어 모델 폴백을 두었고, 대화 히스토리를 서버에 두지 않아 모델을 중간에 바꿔도 맥락이 유실되지 않습니다.

### 에이전트 평가 체계

RAG에서는 검색 실패와 판단 실패가 밖에서 보면 같은 증상을 냅니다. 이 둘을 분리하기 위해 골든 세트에 recall@k·MRR·NDCG를 붙이고, **검색 서비스 직호출과 에이전트 경유 결과를 나란히 측정**해 원인이 검색인지 에이전트인지 판별하도록 만들었습니다.

채점기는 도구 호출 시퀀스·응답 포함 문자열·실행 상한·상태 검사까지 결정론적으로 두고, 응답 품질만 LLM 심판에 맡겼습니다. 지도 조작처럼 응답 텍스트로 검증할 수 없는 도구는 mock 스토어의 최종 상태를 검사해 **말한 것과 실제로 한 것을 분리**했습니다. 검색은 실호출하되 외부 서비스와 화면 조작 도구는 mock으로 두어, 평가 대상과 비용 경계를 명확히 했습니다.

### 자체 운영 클러스터로 이전

서비스는 관리형 조합(서버리스 컨테이너·BaaS 인증·관리형 DB·벡터DB SaaS)으로 시작했다가, 클라우드를 한 번 옮기고 이후 **서빙 스택 전체를 자체 k3s 클러스터로 이전**했습니다. Kustomize base와 환경별 오버레이로 로컬·개발·운영을 같은 매니페스트에서 파생하고, 배포는 셀프호스트 러너가 박스에서 빌드해 클러스터에 직접 적재합니다.

이전의 선행 조건은 인증이었습니다. 앱 테이블이 BaaS 인증 스키마의 유저 UUID에 FK로 묶여 있어 DB를 옮기려면 인증부터 자체 구현해야 했습니다. Auth.js와 Redis 세션 스토어로 다시 세우고, 세션 콜백이 발급하는 단명 앱 JWT를 AI 백엔드가 검증하도록 통일했습니다.

데이터 보호는 사고 시나리오에서 역산해 층을 나눴습니다 — 시점 복구용 물리 백업, 이식 가능한 논리 덤프, 벡터DB 스냅샷, 오브젝트 소프트 삭제. 백업 잡이 아예 돌지 않으면 실패 로그조차 남지 않으므로, **성공 신호의 부재를 경보로 취급하는 deadman 감시**를 붙였습니다. 로그는 요청당 구조화 이벤트 하나로 수집해 조회·알림에 연결했습니다.

## 담당 영역

소규모 팀에서 풀스택을 담당했습니다:

- **AI 백엔드**: LangChain 에이전트 설계, 도구 구현, SSE 스트리밍, 멀티모델 전환
- **전처리 파이프라인**: 크롤러, PDF 파싱과 OCR 조건부 폴백, 청킹·임베딩·벡터화
- **인제스션 오케스트레이션**: Redis 큐 기반 워커 분리, 역압 흐름 제어, GPU 파드 부하 분산과 임베딩 레이트리밋 설계
- **OCR 서비스**: GPU 파드 위에서의 문서 파서 서빙, 추론 최적화, 수요 기반 기동·정지
- **지도·공간 검색**: 지도 도구 설계, 클라이언트 실행 프록시 패턴, 공간 필터 검색
- **평가 체계**: 검색 품질 지표, 결정론적 채점기, 상태 기반 도구 검증
- **프론트엔드**: 챗봇 UI, 이미지 검색 패널, 드래그 앤 드롭 참조
- **인프라**: 자체 클러스터 이전, 인증 자체 구현, 백업·복구 설계, 로그 파이프라인과 알림
