# 학습 데이터를 지키는 방법

어느 날 한 학생의 학습 기록이 이상했다. 테스트를 시작하자마자 모든 문제를 거의 즉시 맞추고 있었다. 확인해보니 브라우저 개발자 도구의 네트워크 탭에서 API 응답을 열어 정답을 미리 보고 있었다. 학원용 학습 앱에서 단어 데이터는 핵심 자산이다. 네트워크 탭에서 답이 그대로 보인다면, 시험의 의미가 없어진다.

## 두 개의 서로 다른 문제

처음에는 하나의 문제로 보였는데, 뜯어보니 성격이 달랐다.

하나는 **시험 중 정답 노출**이다. 문제를 푸는 중에 응답을 열어보면 답이 보인다. 다른 하나는 **데이터 자산의 유출**이다. API를 직접 반복 호출하면 학원이 수년에 걸쳐 구축한 단어장 전체를 긁어갈 수 있다.

둘은 방어 지점이 다르다. 앞은 "무엇을 응답에 담을 것인가"의 문제고, 뒤는 "누가 얼마나 호출할 수 있는가"의 문제다. 하나의 대책으로 둘 다 막으려 하면 어느 쪽도 제대로 막지 못한다.

## 세션 스토어를 두지 않기로 한 이유

가장 먼저 떠오른 건 서버에 세션을 두고 정답을 거기 보관하는 방식이었다. 당연히 고려했다.

그런데 서비스는 서버리스 환경에서 돌고 있었고, 세션 스토어로 쓸 인프라가 없었다. 이 문제 하나 때문에 상시 운영해야 할 구성 요소를 추가하면, 이후로 그걸 계속 돌보고 비용을 내야 한다. **문제의 크기에 비해 감당할 짐이 컸다.** 주어진 자원 안에서 풀 수 있으면 그게 낫다고 봤다.

## 구조를 바꾸면 지킬 것이 줄어든다

그래서 방향을 틀었다. 정답을 **어떻게 숨길까**가 아니라, 애초에 **정답이 나가지 않게** 할 수 없을까.

클라이언트에는 문제와 뒤섞인 선택지만 보낸다. 어느 것이 정답인지는 응답 어디에도 없다. 학생이 답을 고르면 서버로 보내고, **판정은 서버에서만** 한다. 네트워크 탭을 열어도 정답을 특정할 근거가 응답 안에 존재하지 않는다.

이 전환이 핵심이었다. 숨겨야 할 것이 응답에 남아 있으면 그걸 지키는 장치가 계속 필요하지만, 아예 담기지 않으면 지킬 것 자체가 없어진다. **보안 장치를 더하는 대신, 지켜야 할 대상을 줄이는 쪽**이 구조적으로 더 단단했다.

## 나머지는 계층으로 막는다

정답 노출은 구조로 해결됐지만, 데이터 유출은 별개다. 여기는 단일 방어선에 기대지 않고 층을 나눴다.

인증으로 **누가** 호출하는지를 제한하고, 전송 구간을 보호하고, 응답 본문 자체도 평문으로 두지 않는다. 각 층이 서로 다른 공격 경로를 담당한다. 인증을 통과해도 응답을 그대로 읽을 수 없고, 응답을 가로채도 의미 있는 형태가 아니다.

한 세션 분량의 문제를 한꺼번에 내려주지 않는 것도 같은 맥락이다. 지금 풀고 있는 문제만 전달하고, 답을 확인한 뒤 다음을 준다. 한 번의 요청으로 가져갈 수 있는 양을 줄이면, 긁어가는 비용이 올라간다.

토큰이 비정상이면 해당 학습 세션을 즉시 무효화한다. 조작된 요청으로 점수를 올리는 경로 자체를 닫아둔 것이다.

## 돌이켜보면

시작은 **"학생이 네트워크 탭에서 답을 보고 있다"**는 실제 사건이었다. 처음에는 응답을 어떻게 가릴지만 생각했는데, 결국 답이 된 건 **응답에서 정답을 빼버리는 것**이었다.

보안을 장치의 문제로만 보면 계속 덧붙이게 된다. 그보다 먼저 물어야 할 건 "이걸 꼭 내보내야 하는가"였다. 내보내지 않아도 되는 것을 찾아내면, 지켜야 할 범위가 줄고 남은 것에 집중할 수 있다.
