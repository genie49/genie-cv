# GPU를 빌리는 방식을 두 번 바꿨다

발굴보고서 PDF를 텍스트로 바꾸려면 OCR이 필수다. 문제는 문서 파싱 모델이 GPU를 요구한다는 점이었다. 상시 GPU 서버를 운영하면 비용이 크고, 보고서 처리는 초기 일괄 인제스션 이후에는 간헐적으로만 발생한다. **안 쓸 때 비용이 0인 구조**가 필요했다.

## Modal 서버리스를 선택한 이유

GPU 서빙 선택지는 크게 세 가지였다.

| 선택지 | 장점 | 단점 |
|--------|------|------|
| AWS EC2 GPU 인스턴스 | 안정적, 커스텀 자유 | 상시 비용, 유휴 시간에도 과금 |
| 시간당 과금 GPU 파드 | 콜드 스타트 없음 | 켜고 끄는 걸 직접 관리 |
| **Modal 서버리스** | 요청 시만 GPU 할당, 자동 스케일링 | Cold start 존재 |

Modal을 택한 결정적 이유는 **컨테이너 수준의 커스텀이 가능하면서도 서버리스**라는 점이었다. CUDA 베이스 이미지 위에 추론 엔진과 문서 파서를 직접 설치하고, 내부에서 추론 서버를 프로세스로 띄우는 구조까지 자유롭게 구성할 수 있었다.

## 추론 엔진을 따로 둔 이유

문서 파서는 내부적으로 VLM(Vision Language Model)을 사용한다. 기본 추론 백엔드 대신 vLLM을 얹은 이유는 **배치 추론 시 throughput 극대화** 때문이었다.

파서의 내부 파이프라인은 입력 준비 → 레이아웃 분석 → VLM 추론 순으로 동작하며, VLM 단계에서 여러 요청을 자동으로 미니배칭한다. 이때 vLLM의 continuous batching이 배치 효율을 크게 높여준다. VLM 동시 요청 수에 상한을 두어, 레이아웃 분석이 끝난 블록들이 대기 없이 추론으로 흘러가도록 했다.

## 무엇을 깎고 무엇을 살릴지

추론 설정은 결국 **이 워크로드에서 무엇을 포기해도 되는가**의 문제였다.

- **KV 캐시 정밀도를 낮췄다.** OCR은 창의적인 생성이 아니라 텍스트 인식이 목적이라, 정밀도를 한 단계 깎아도 결과가 나빠지지 않았다. 대신 캐시 메모리가 절반으로 줄어 동시에 처리할 수 있는 시퀀스가 늘었다. **정밀도를 팔아 처리량을 산 것**이다.
- **프리필을 잘게 나눴다.** 보고서 페이지 이미지는 토큰 수가 많아 프리필 단계가 길다. 프리필을 청크로 쪼개 디코딩과 번갈아 처리하면 첫 토큰까지의 지연이 줄어든다.
- **프리픽스 캐시는 껐다.** 페이지마다 이미지가 전부 다르니 공유할 프리픽스가 없다. 히트율이 0인 캐시는 오버헤드일 뿐이라 꺼두는 쪽이 이득이었다.
- **GPU 메모리는 공격적으로 잡았다.** 모델 크기에 비해 VRAM에 여유가 있어, 점유율을 높게 잡아도 OOM 없이 안정적으로 돌았다.

일반적인 서빙 튜닝 가이드를 그대로 따르는 대신, **OCR이라는 작업의 성질**에 맞춰 하나씩 정한 값들이다.

## 실제로 얼마나 나왔나

이 구성에서 PDF 문서 100건(문서당 200~300페이지)을 처리한 결과다.

| 지표 | 수치 |
|------|------|
| Cold start | ~30초 |
| 40페이지 추론 | ~1분 30초 (페이지당 ~3.1초) |
| 117페이지 추론 | ~394초 (페이지당 ~3.4초) |
| GPU 비용 | L40S ~$0.83/시간 |
| 월 운영 비용 | 무료 크레딧 $30/월 내 |

주목한 건 **페이지 수가 세 배 가까이 늘어도 페이지당 시간이 3.1초에서 3.4초로 거의 그대로**라는 점이다. continuous batching이 배치 효율을 일정하게 유지해 주기 때문인데, 이 수치를 확인하고 나서야 "문서를 더 밀어 넣어도 선형으로만 늘어난다"는 확신이 생겼다.

## 그런데 GPU가 놀고 있었다

8,000건 규모로 인제스션을 시작하니 다른 그림이 보였다. 페이지를 아무리 밀어 넣어도 처리량이 어느 선에서 더 올라가지 않았다.

원인은 파서의 구조에 있었다. 레이아웃 분석은 CPU에서, 텍스트 인식만 GPU에서 도는 2단계 구조라 **CPU가 처리량 상한을 정하고 있었다.** 레이아웃 단계만 떼어내 벤치를 떠보니 명확했다. GPU를 아무리 좋은 걸로 바꿔도 앞단이 못 따라오면 소용이 없다.

## 레이아웃부터 읽기 순서까지 한 모델이 하도록

파서를 dots.ocr로 갈아끼웠다. 레이아웃 감지, 텍스트 인식, 읽기 순서 정렬을 **하나의 VLM이 GPU에서 한 번에** 처리하는 모델이다. CPU 단계 자체가 사라지니 병목도 같이 사라졌다.

덕분에 OCR 서버는 **얇은 어댑터**가 됐다. 페이지 이미지를 추론 서버에 던지고, 돌아온 레이아웃 JSON을 기존 계약 — 마크다운 텍스트 + 이미지 bbox — 으로 변환하는 게 전부다. 파서를 통째로 바꿨는데 **호출하는 쪽 파이프라인은 한 줄도 고치지 않았다.** 응답 형식을 먼저 계약으로 못 박아 둔 덕분이었다.

한 가지 함정이 있었다. 모델은 내부에서 리사이즈한 이미지 기준으로 bbox를 뱉는데, 호출자는 자기가 보낸 원본 크기로 crop한다. 좌표계가 어긋나면 엉뚱한 영역이 잘린다. 리사이즈 파라미터를 추론 서버에 명시적으로 고정해 두고, 어댑터가 같은 계산을 복제해 원본 좌표로 역산했다. **양쪽이 같은 규칙을 쓰도록 만들어 매핑을 결정적으로** 만든 것이다.

가중치 정밀도도 한 단계 낮췄다. KV 캐시 때와 같은 판단이었고, 처리량이 **1.62배**로 올라갔다.

## 그리고 서버리스를 떠났다

모델을 바꾸면서 과금 방식도 다시 봤다. 초기 인제스션은 8,000건을 며칠에 걸쳐 연속으로 밀어 넣는 작업이다. 이 구간에서는 GPU가 계속 바쁘다. **요청이 없을 때 0원인 구조의 이점이 나올 자리가 없다.**

그래서 처음 비교표에서 제쳐뒀던 선택지로 돌아갔다. 시간당 과금 GPU 파드를 여러 대 띄우고, 콜드 스타트 없이 계속 워밍된 상태로 문서를 밀어 넣는 방식이다.

## "안 쓸 때 0원"은 직접 만들었다

대신 서버리스가 대신 해주던 일을 직접 해야 했다. 파드 매니저를 두고 **큐 길이를 보고 켜고 끈다.** 처리할 문서가 쌓이면 파드를 기동하고, 유휴 상태가 일정 시간 이어지면 정지시킨다. 파드를 지우는 게 아니라 정지만 하기 때문에 네트워크 볼륨에 올려둔 실행 환경과 모델 가중치가 그대로 남고, 다음 기동이 빠르다.

결과적으로 같은 목표에 도달했다. 다른 건 **스위치가 내 손에 있다는 점**이다. 무엇을 수요로 볼지, 얼마나 기다렸다 끌지를 워크로드에 맞춰 정할 수 있게 됐다.

여러 대를 동시에 쓰니 분배도 필요했다. 문서를 페이지 배치로 쪼개 **in-flight가 가장 적은 파드로 보내는** 프록시를 앞에 뒀다. 문서 크기 편차가 커도 자동으로 균형이 맞는다. 완료된 문서는 체크포인트에 기록해서, 중간에 끊겨도 다시 돌리면 남은 것부터 이어간다.

## 인프라가 조용히 매달리는 순간들

직접 관리하기로 한 대가는 곧 청구됐다.

**네트워크 볼륨이 매달렸다.** 볼륨에 올려둔 모델로 추론 서버를 띄우면 로딩 도중 무한 대기에 빠졌다. GPU 사용률 0, 읽은 바이트도 멈춘 채로. 작은 설정 파일 읽기는 멀쩡한데 큰 가중치를 mmap으로 올리는 구간에서만 멈췄다. 그런데 같은 볼륨에서 **순차 복사는 초당 수백 MB로 멀쩡히 빨랐다.** 그래서 기동 직전에 모델을 컨테이너 로컬 디스크로 복사한 뒤 거기서 띄우는 것으로 우회했다.

**죽은 엔진이 GPU를 인질로 잡았다.** 재기동할 때마다 새 엔진이 OOM으로 죽었다. 이전 세대의 추론 엔진 프로세스가 살아남아 VRAM을 점유하고 있었는데, 프로세스 이름이 예상과 다른 대소문자라 평범한 정리 명령에 걸리지 않았다. 기동 스크립트가 대소문자를 무시하고 잔재를 정리한 뒤, GPU 메모리가 실제로 회수됐는지 확인하고 나서야 다음 단계로 넘어가도록 바꿨다.

둘 다 모델이나 코드의 문제가 아니라 **빌린 인프라의 성질** 때문에 생긴 일이었다. 서버리스를 쓸 때는 플랫폼이 감춰주던 층이다.

## 돌아보면

질문이 "서버리스냐 상시냐"인 줄 알았는데, 실제로는 **워크로드가 지금 어느 구간에 있느냐**였다.

8,000건을 밀어 넣는 초기 인제스션 구간에서는 계속 워밍된 파드가 맞고, 신규 보고서가 가끔 등록되는 이후 구간에서는 껐다 켜는 게 맞다. 한쪽을 고르는 문제가 아니라 **구간마다 다른 답을 쓸 수 있게 만드는 문제**였고, 그래서 켜고 끄는 판단을 코드로 가져오는 쪽으로 갔다.
