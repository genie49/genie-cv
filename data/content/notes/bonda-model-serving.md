# 서버리스 GPU에서 OCR 모델 서빙하기

발굴보고서 PDF를 텍스트로 바꾸려면 OCR이 필수다. 문제는 문서 파싱 모델이 GPU를 요구한다는 점이었다. 상시 GPU 서버를 운영하면 비용이 크고, 보고서 처리는 초기 일괄 인제스션 이후에는 간헐적으로만 발생한다. **안 쓸 때 비용이 0인 구조**가 필요했다.

## Modal 서버리스를 선택한 이유

GPU 서빙 선택지는 크게 세 가지였다.

| 선택지 | 장점 | 단점 |
|--------|------|------|
| AWS EC2 GPU 인스턴스 | 안정적, 커스텀 자유 | 상시 비용, 유휴 시간에도 과금 |
| RunPod/Banana 등 추론 API | 간편한 배포 | 커스텀 파이프라인 제약, 벤더 종속 |
| **Modal 서버리스** | 요청 시만 GPU 할당, 자동 스케일링 | Cold start 존재 |

Modal을 택한 결정적 이유는 **컨테이너 수준의 커스텀이 가능하면서도 서버리스**라는 점이었다. CUDA 베이스 이미지 위에 추론 엔진과 문서 파서를 직접 설치하고, 내부에서 추론 서버를 프로세스로 띄우는 구조까지 자유롭게 구성할 수 있었다.

## 추론 엔진을 따로 둔 이유

문서 파서는 내부적으로 VLM(Vision Language Model)을 사용한다. 기본 추론 백엔드 대신 vLLM을 얹은 이유는 **배치 추론 시 throughput 극대화** 때문이었다.

파서의 내부 파이프라인은 입력 준비 → 레이아웃 분석 → VLM 추론 순으로 동작하며, VLM 단계에서 여러 요청을 자동으로 미니배칭한다. 이때 vLLM의 continuous batching이 배치 효율을 크게 높여준다. VLM 동시 요청 수에 상한을 두어, 레이아웃 분석이 끝난 블록들이 대기 없이 추론으로 흘러가도록 했다.

## 무엇을 깎고 무엇을 살릴지

추론 설정은 결국 **이 워크로드에서 무엇을 포기해도 되는가**의 문제였다.

- **KV 캐시 정밀도를 낮췄다.** OCR은 창의적인 생성이 아니라 텍스트 인식이 목적이라, 정밀도를 한 단계 깎아도 결과가 나빠지지 않았다. 대신 캐시 메모리가 절반으로 줄어 동시에 처리할 수 있는 시퀀스가 늘었다. **정밀도를 팔아 처리량을 산 것**이다.
- **프리필을 잘게 나눴다.** 보고서 페이지 이미지는 토큰 수가 많아 프리필 단계가 길다. 프리필을 청크로 쪼개 디코딩과 번갈아 처리하면 첫 토큰까지의 지연이 줄어든다.
- **프리픽스 캐시는 껐다.** 페이지마다 이미지가 전부 다르니 공유할 프리픽스가 없다. 히트율이 0인 캐시는 오버헤드일 뿐이라 꺼두는 쪽이 이득이었다.
- **GPU 메모리는 공격적으로 잡았다.** 모델 크기에 비해 VRAM에 여유가 있어, 점유율을 높게 잡아도 OOM 없이 안정적으로 돌았다.

일반적인 서빙 튜닝 가이드를 그대로 따르는 대신, **OCR이라는 작업의 성질**에 맞춰 하나씩 정한 값들이다.

## 스케일링과 Cold Start

일괄 처리 시에는 인스턴스를 여러 개 병렬로 띄워 문서를 동시에 처리했다. 각 인스턴스가 독립적인 GPU와 추론 서버를 갖고 있어 인스턴스 간 간섭이 없다.

Cold start는 **30초 안팎**이 걸린다. 모델 가중치는 영구 볼륨에 캐싱해 두어 네트워크 다운로드를 건너뛰고, 남은 시간의 대부분은 추론 서버 초기화(모델 로드와 커널 컴파일)에 쓰인다. 유휴 시간이 몇 분 이어지면 인스턴스가 자동으로 내려가도록 두어, 배치 처리 중에는 계속 살아 있고 끝나면 알아서 꺼진다.

## 결국 워크로드의 성질 문제였다

이 구조가 성립한 건 **작업의 성격 덕분**이었다. Cold start 30초는 실시간 응답이 필요한 서비스였다면 치명적이다. 하지만 문서 수백 건을 밀어 넣는 배치 파이프라인에서는 맨 처음 한 번만 발생하고, 이후로는 인스턴스가 warm 상태로 유지된다. 전체 처리 시간에 비하면 무시할 수 있는 비용이었다.

처리량 면에서도 페이지가 늘어난다고 페이지당 시간이 크게 나빠지지 않았다. continuous batching이 배치 효율을 일정하게 유지해 주기 때문이다. 초기 인제스션이 끝난 뒤에는 신규 보고서가 등록될 때만 간헐적으로 GPU가 켜지는 패턴이라, 유휴 시간이 대부분인 워크로드였다.

## 돌아보면

서버리스 GPU의 핵심 가치는 **"안 쓸 때 비용이 0"**이라는 점이었다. 상시 GPU 서버였다면 쓰지 않는 시간까지 고정 비용으로 나갔을 텐데, 실제 추론 시간에만 과금되는 구조를 만들 수 있었다.

같은 인프라가 어떤 서비스에는 최악이고 어떤 서비스에는 최적이다. Cold start를 감당할 수 있는가, 유휴 시간이 얼마나 되는가 — **워크로드의 성질을 먼저 보고 인프라를 고르는 것**이 순서였다.
