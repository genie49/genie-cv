# 검색이 틀린 건지 에이전트가 틀린 건지

RAG 시스템에서 답이 이상하게 나왔을 때, 원인은 크게 두 갈래다. 필요한 문서를 못 찾아온 것과, 찾아왔는데 제대로 못 쓴 것. 그런데 **밖에서 보면 증상이 똑같다.** 둘 다 "엉뚱한 소리를 한다"로 보인다.

프롬프트를 고쳤는데 나아지지 않으면 검색을 의심하고, 검색을 손봤는데 그대로면 다시 프롬프트로 돌아온다. 이 왕복을 몇 번 하고 나서 **둘을 따로 재기로** 했다.

## 검색은 검색대로 숫자로 잰다

질문과 정답 문서 쌍을 모아 골든 세트를 만들고, 검색 결과에 recall@k·MRR·NDCG를 붙였다. 여기까지는 정보 검색의 교과서적인 지표다.

의미가 생긴 건 **같은 질문을 두 경로로 재면서**다. 검색 서비스를 직접 호출한 결과와, 에이전트를 거쳐 나온 결과를 나란히 놓는다.

| 컴포넌트 | E2E | 해석 |
|---|---|---|
| 낮음 | 낮음 | 검색 문제 — 청킹·임베딩·필터를 봐야 한다 |
| 높음 | 낮음 | 에이전트 문제 — 질의를 이상하게 만들었거나 필터를 잘못 걸었다 |
| 높음 | 높음 | 검색은 됐다. 답이 이상하면 그건 생성 문제다 |

이 표 하나로 **어디를 볼지가 정해진다.** 그전까지는 감으로 골랐다.

## 무엇을 진짜로 호출할 것인가

평가 환경을 만들 때 가장 오래 고민한 게 이거였다. 전부 mock으로 두면 빠르고 싸지만 진짜 검색 품질은 못 잰다. 전부 실호출하면 느리고 비싸고, 외부 서비스 상태에 따라 결과가 흔들린다.

경계를 이렇게 그었다. **검색은 실제로 부른다.** Bonda에서 검색은 부수 기능이 아니라 제품 그 자체라, 여기를 mock으로 대체하면 평가가 재는 게 없어진다. 반면 지도 조작이나 외부 웹 검색은 mock으로 뒀다. 이쪽은 **에이전트가 올바른 도구를 올바른 인자로 불렀는지**가 관심사지, 그 도구가 실제로 뭘 반환하는지는 관심사가 아니기 때문이다.

## 텍스트가 아니라 상태를 채점한다

지도 도구를 평가하면서 알게 된 게 있다. **응답 텍스트로는 채점이 안 된다.** 에이전트가 "핀을 찍었습니다"라고 말했다고 해서 실제로 찍힌 게 아니다.

그래서 mock 스토어의 **최종 상태**를 검사하는 채점기를 뒀다. 경로를 점 표기로 지정하고 기대값을 거는 방식이다. 임시 핀이 하나 이상 찍혔는가, 특정 리스트에 멤버가 들어갔는가 같은 것들.

말한 것과 한 것을 갈라서 보게 되니, **말은 맞는데 실행이 빠진 경우**가 실제로 잡혔다.

## 채점기는 여럿, LLM 심판은 하나

채점기를 여러 개 두되 **LLM을 쓰는 건 하나만** 남겼다. 도구 호출 시퀀스, 응답에 포함돼야 할 문자열, 턴·호출 수 상한, 상태 검사까지는 전부 순수 파이썬이다. 공짜고, 빠르고, 무엇보다 **같은 입력에 같은 결과가 나온다.**

응답 품질처럼 사람 판단이 필요한 축만 LLM 심판에 맡겼다. 평가 시스템 자체가 흔들리면 무엇을 고쳐야 할지 알 수 없으니, 흔들리는 부분을 최소한으로 몰아넣는 게 목적이었다.

도구 호출 채점에서는 **얼마나 엄격할지를 태스크마다 고를 수 있게** 했다.

- 순서까지 정확히 / 순서 무관 / 최소한 이건 불렀는가 / 이것 외엔 부르지 말 것
- 인자는 와일드카드, 비교식, 정규식으로 매칭

처음엔 인자까지 정확히 일치시켰는데, 에이전트가 검색어를 조금만 다르게 만들어도 실패했다. **틀린 게 아닌데 실패하는 평가는 금방 아무도 안 본다.** 검증하려는 게 "정확히 이 문자열"이 아니라 "이 필터가 걸렸는가"라면 매처도 거기에 맞춰야 했다.

## 비싼 일과 싼 일을 티어로 갈랐다

평가를 자주 돌리려면 한 번 도는 비용이 싸야 한다. 그런데 정성 채점, 골든 질문 생성, 결과 분석은 전부 LLM이 필요한 일이다.

그래서 실행을 두 티어로 나눴다. **일상적으로 도는 티어**는 결정론적 채점과 검색 지표가 중심이고, LLM이 필요한 정성 작업은 개발 도구의 서브에이전트에 맡긴다 — 답변 생성, 채점, 분석을 각각 다른 역할로 두고 돌린다. 불가피하게 API를 쓰는 건 임베딩뿐인데, 이건 벡터DB와 같은 모델을 써야 해서 대체 불가고 건당 비용도 무시할 만하다.

**프로덕션 에이전트를 그대로 돌리는 티어**는 따로 두되 자주 돌리지 않는다. 이 티어의 역할은 회귀 탐지가 아니라 **대리 지표가 여전히 유효한지 확인하는 것**이다. 일상 티어가 프로덕션 경로와 벌어지기 시작하면 그때 알아야 하니까.

## 실패했을 때 무엇을 고칠 것인가

평가를 붙이고 나서 가장 자주 마주친 판단은 "이 실패가 에이전트 잘못인가, 기대값 잘못인가"였다.

커버리지를 넓히려고 태스크를 추가할 때, 기대값은 결국 **내가 상상한 풀이 방식**이다. 그런데 에이전트는 종종 다르게 푼다. 도구를 하나 덜 부르고 답을 맞히기도 하고, 순서를 바꿔 부르기도 한다.

여기서 기대값을 그대로 두고 에이전트를 맞추려 들면 **평가가 설계를 강제하게 된다.** 그래서 신규 태스크는 실제 동작을 먼저 관찰하고, 그게 합리적이면 기대값을 실측에 맞춰 보정했다. 평가가 잡아야 하는 건 "내가 예상한 대로 안 했다"가 아니라 **"결과가 틀렸다"**여야 한다.

## 돌이켜보면

평가 체계를 만들면서 얻은 건 점수 자체가 아니라 **원인을 가르는 능력**이었다. 검색과 판단을 나눠 재고, 말한 것과 실행한 것을 나눠 채점하고, 결정론적인 부분과 흔들리는 부분을 나눠 두는 것 — 전부 같은 얘기다.

디버깅이 오래 걸리는 이유는 보통 문제가 어려워서가 아니라, **어디를 봐야 할지 모르기 때문**이다.
