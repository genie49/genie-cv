# AI를 시스템에 맞추지 말고, 시스템을 AI에게 맞춰라

처음에는 기존 시스템에 AI를 끼워 넣으려 했다. 실시간 채널 안에서 에이전트를 실행하고, LangGraph의 state에 작업 데이터를 담고, 프레임워크가 제공하는 방식대로 동작하게 만들었다. 그런데 AI는 기존 시스템의 가정과 맞지 않았다. **시스템에 AI를 맞추니 성능도 UX도 나빠졌다.** 결국 시스템을 AI에 맞춰 다시 설계하게 된 과정을 정리한다.

## 실시간 채널이 전부 하던 시절

처음 구조는 단순했다. 하나의 서비스가 WebSocket으로 사용자와 연결되고, 같은 프로세스에서 AI 에이전트를 실행하고, 결과를 사용자에게 전달했다. 실시간 상태 전달과 AI 실행을 한 덩어리가 다 맡은 셈이다.

문제는 **두 역할의 관심사가 완전히 다르다**는 점이었다. 실시간 전달은 지금 무슨 일이 일어나고 있는지를 계속 흘려보내는 게 핵심이다. 가벼워야 하고, 연결이 안정적이어야 한다. 반면 에이전트 실행은 LLM을 돌리고, 도구를 호출하고, 서브에이전트를 관리하는 무거운 작업이다. 미들웨어, 스냅샷, 에러 복구 같은 복잡한 인프라가 필요하다.

둘이 한 프로세스에 묶여 있으니 **양쪽 다 발전시키기 어려웠다.** 실행 쪽에 미들웨어를 추가하면 연결 안정성에 영향을 줄까 걱정해야 했고, 연결을 스케일링하면 LLM 부하까지 따라 올라갔다. 종속성이 높아질수록 에이전트 인프라(harness)를 자유롭게 설계하기 어려워졌다.

## 관심사를 분리하다

MSA의 기본 원칙대로 관심사를 나눴다. 한쪽은 **실시간 전달**에 집중하고, 다른 쪽은 **에이전트 실행**에 집중한다. 분리하니까 실행 쪽에서 미들웨어 파이프라인, 스냅샷 시스템, 서브에이전트 오케스트레이션 같은 harness를 자유롭게 설계할 수 있게 됐다. 연결 안정성을 걱정하지 않아도 됐다.

그런데 분리된 둘을 어떻게 이을 것인가.

## 분리된 둘 사이에 메시지 큐를 놓다

HTTP 호출은 옵션이 아니었다. LLM은 한 번의 응답을 생성하는 데 **수십 초에서 수 분**이 걸린다. 그 동안 HTTP 커넥션을 붙잡고 있어야 하고, 실행 워커가 재시작되면 커넥션이 끊기면서 진행 중인 응답이 유실된다.

**메시지 큐**를 사이에 놓았다. 실행 쪽이 메시지를 발행하면 실시간 채널이 구독해서 사용자에게 전달한다. 워커가 재시작되어도 WebSocket 연결은 유지되고, 메시지는 버퍼링된다.

여기에 다대다 통신 요구도 있었다. 같은 작업을 여러 사용자가 동시에 보는 경우, 하나의 실행 결과가 **여러 채널 인스턴스에 동시에 전달**되어야 한다. 메시지 속성 기반 필터링으로, 단일 토픽에서 인스턴스별 라우팅을 해결했다.

독립 스케일링은 분리의 부산물이었다. 연결 수가 늘면 채널만 스케일아웃하고, LLM 부하가 늘면 실행 워커만 추가하면 된다.

## 인스턴스가 여러 개면, 누가 어디 있는지 어떻게 아는가

채널 인스턴스와 실행 워커가 여러 개 떠 있다고 하자. 사용자 A는 그중 특정 채널 인스턴스에 연결되어 있고, 그 요청은 임의의 워커가 처리한다. 워커가 결과를 발행하면 **A가 붙어 있는 바로 그 인스턴스**가 받아야 한다. 다른 인스턴스가 받으면 소용이 없다 — A의 WebSocket 연결은 거기에만 있으니까.

속성 필터링만으로는 부족했다. 어떤 인스턴스가 어떤 사용자를 담당하고 있는지를 **동적으로 알아야** 한다. 인스턴스는 스케일링에 따라 생겼다 사라지니까.

**인메모리 저장소 기반 서비스 디스커버리**로 해결했다. 각 인스턴스는 시작 시 자신을 레지스트리에 등록하고, 주기적으로 heartbeat를 갱신한다. 사용자가 연결되면 "이 사용자는 이 인스턴스에 있다"는 매핑이 기록된다. 워커가 결과를 발행할 때 이 매핑을 조회해서, 해당 인스턴스가 구독하는 채널로 정확히 라우팅한다.

같은 작업을 여러 사용자가 동시에 보는 경우도 있다. 이때는 작업 단위로 연결된 사용자를 모두 조회하고, 각자가 붙어 있는 인스턴스로 **팬아웃**한다. 인스턴스가 죽으면 heartbeat가 만료되면서 자동으로 레지스트리에서 제거된다. 새 인스턴스가 뜨면 등록만 하면 된다 — 기존 인스턴스의 설정을 건드릴 필요가 없다.

수평 확장의 핵심은 **인스턴스 간 직접 통신이 없는 것**이었다. 모든 라우팅 정보가 레지스트리에 있고, 메시지는 큐를 거친다. 채널을 몇 배로 늘려도 워커 코드는 한 줄도 바뀌지 않는다.

## AI는 병렬로 일한다, 그런데 state가 허락하지 않았다

서비스 분리는 끝났다. 다음 문제는 실행 서비스 내부에서 터졌다.

에이전트가 도구를 호출할 때, 오케스트레이터가 "이것도 하고 저것도 해"라고 판단하면 여러 서브에이전트가 **동시에** 실행된다. 각각이 같은 작업 데이터를 수정한다. 문제는 LangGraph의 state 관리 방식이었다.

**LangGraph state는 replace 방식**이다. 작업 데이터 전체를 하나의 state로 담고, 도구가 결과를 반환하면 통째로 교체한다. 두 도구가 병렬로 실행되면, 먼저 끝난 쪽의 변경이 나중에 끝난 쪽에 의해 **덮어써진다.** 데이터 유실.

첫 번째 시도는 **AI를 시스템에 맞추는 것**이었다. 도구가 직접 state를 수정하는 대신, 변경사항을 배열로 만들어서 반환하게 했다. 이렇게 하면 state 충돌은 피할 수 있지만, **병렬 도구 호출을 포기해야 했다.** 순차 실행.

결과는 처참했다. **속도가 약 2.5배 느려졌다.** 여러 서브에이전트가 동시에 도구를 호출하던 것을 하나씩 순서대로 실행하니 당연한 결과였다. 성능만 나빠진 게 아니었다. UX도 달라졌다. 병렬이면 여러 작업 시작 알림이 거의 동시에 뜨면서 AI가 활발하게 일하는 느낌이었는데, 순차로 바꾸니 **한참 조용하다가 갑자기 결과가 툭 나타나는** 느낌이었다.

2.5배의 속도와 실시간 피드백의 생동감. 이걸 포기할 수 없었다.

## 시스템을 AI에게 맞추다

발상을 바꿨다. LangGraph state에 맞추지 말고, **state를 대체하자.**

워크플로우가 시작되면 작업 데이터를 **인메모리 저장소에 스냅샷**으로 복사한다. 이후 모든 변경은 거기에만 기록한다. 핵심은 **변경 리스트**다. 도구가 데이터를 수정할 때 전체를 교체하는 게 아니라, 필드 단위 변경을 리스트에 순서대로 쌓는다.

| LangGraph state (Before) | 스냅샷 + 변경 리스트 (After) |
|---|---|
| 전체 교체 (replace) | 필드 단위 추가 (append) |
| 병렬 쓰기 시 덮어씀 | 병렬 쓰기가 리스트에 순서대로 쌓임 |
| 병렬 도구 호출 불가 | 병렬 도구 호출 가능 |

읽기할 때는 원본 스냅샷에 변경분을 순서대로 적용한 결과를 반환한다. 한 서브에이전트가 어떤 필드를 수정한 뒤 다른 서브에이전트가 같은 필드를 읽으면 최신 값을 볼 수 있다.

같은 필드를 두 에이전트가 동시에 수정하면? 이론적으로는 나중에 쓴 값이 이기지만, 실제로는 일어나지 않는다. 각 서브에이전트의 도구에 **쓰기 가능한 영역 제한**이 걸려 있기 때문이다. 분석 담당은 분석 영역만, 기획 담당은 기획 영역만 수정할 수 있다. 도구 레벨에서 영역을 격리하면 물리적으로 같은 필드를 건드리는 일이 발생하지 않는다.

워크플로우가 정상 완료되면 스냅샷과 변경분을 합산해서 DB에 한 번에 커밋한다. 실패하면 임시 상태만 정리하면 된다 — DB는 아직 건드리지 않았으므로 원본이 안전하다.

## 돌이켜보면

두 번의 설계 전환이 있었다. 실시간 전달과 에이전트 실행을 분리한 것, 그리고 LangGraph state를 자체 스냅샷으로 대체한 것. 둘 다 같은 깨달음에서 나왔다. **AI를 기존 시스템의 제약에 맞추면, AI가 할 수 있는 것의 상당 부분을 포기하게 된다.**

기존 HTTP 통신에 맞추면 AI의 긴 처리 시간과 실시간 스트리밍을 포기해야 했다. LangGraph state에 맞추면 병렬 실행과 실시간 피드백을 포기해야 했다. 시스템을 AI에 맞춰 다시 설계하니, 포기했던 것들이 돌아왔다.
