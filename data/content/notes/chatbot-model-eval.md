# 모델을 바꾸기 전에 실험부터 짰다

새 모델이 나왔다는 소식을 봤다. 벤치마크 점수는 더 높았고, 비교 글도 여럿 있었다. 그런데 그 숫자들이 **이 챗봇에서도 그럴 거라는 보장은 없었다.**

이 챗봇이 실제로 하는 일은 좁다. 한국어 포트폴리오 문서를 벡터 검색해서, 방문자 질문에 근거만 가지고 답하고, 모르면 모른다고 하는 것. 범용 지능 지표가 여기서 무슨 의미가 있는지 알 수 없었다. 그래서 **이 챗봇 자체를 실험 대상으로 삼기로** 했다.

## 무엇만 바꿀 것인가

실험의 절반은 **바꾸지 않을 것을 정하는 일**이었다.

시스템 프롬프트, RAG 도구, 벡터DB, 질문 목록, 질문 순서를 전부 고정하고 **LLM만** 교체했다. 프로덕션 코드의 에이전트를 그대로 불러 쓰되 모델 인스턴스만 갈아끼우는 방식이라, 측정한 차이가 모델 말고 다른 데서 올 여지를 없앴다.

## 무엇을 물어볼 것인가

질문을 아무거나 던지면 "둘 다 그럴듯하게 답한다"로 끝난다. 그래서 **이 챗봇이 실패할 수 있는 방식**을 먼저 나열하고, 각각을 겨냥한 케이스를 만들었다.

| 카테고리 | 겨냥한 실패 | 채점 방법 |
|---|---|---|
| 사실검색 | 문서에 있는데 못 찾는다 | 기대 키워드 포함 여부 |
| 종합 | 여러 문서를 못 엮는다 | 필수 + 선택 키워드 |
| 환각저항 | 없는 걸 지어낸다 | 모른다고 하거나 전제를 바로잡음 |
| 도구판단 | 인사말에도 검색을 부른다 | 도구 호출 0회 |
| 멀티턴 | 후속 질문에서 맥락을 잃는다 | 대명사 해소 후 검색 |

환각저항에는 일부러 **없는 사실**을 물었다. 토익 점수, 쓰지도 않은 메시지 큐, 존재하지 않는 프로젝트. 도구판단에는 "안녕하세요"와 "고마워요"를 넣었다 — 검색이 필요 없는데 부르면 지연과 비용만 늘어난다.

채점은 전부 결정론적으로 짰다. LLM 심판을 쓰면 채점기 자체가 흔들려서 무엇을 고칠지 알 수 없어진다.

케이스 12개 × 모델 2개 × 3회 반복 = **대화 72회**를 돌렸다.

## 채점기가 먼저 틀렸다

결과를 보니 새 모델이 환각저항에서 두 번 실패해 있었다. 원문을 열어봤더니 이렇게 답하고 있었다.

> "Bonda에서는 Kafka 대신 **Redis 큐**를 사용하여 인제스션 파이프라인을 구축했습니다."

**이건 오답이 아니라 더 나은 답이었다.** 나는 "모른다고 답하기"만 정답으로 인정하도록 채점기를 짰는데, 실제로는 **틀린 전제를 바로잡는 쪽**이 사용자에게 훨씬 유용하다.

여기서 배운 게 있다. 평가를 만들면 처음 기대값은 결국 **내가 상상한 정답 형태**다. 실패를 보고 모델을 고칠지 채점기를 고칠지 판단하는 게 실험의 절반이었다. 기준을 고치고 저장해둔 응답을 다시 채점했다 — 답변 원문을 전부 저장해뒀기 때문에 API를 다시 부르지 않고 재채점만 하면 됐다.

## 결과

| 카테고리 | 기존 모델 | 새 모델 |
|---|---|---|
| 사실검색 | 10/12 | **12/12** |
| 종합 | 5/6 | **6/6** |
| 환각저항 | 9/9 | 9/9 |
| 도구판단 | 6/6 | 6/6 |
| 멀티턴 | **0/3** | **3/3** |
| **전체** | 30/36 | **36/36** |

멀티턴 0/3이 눈에 걸렸다. 3회 모두 실패한다는 건 우연이 아니라는 뜻이라, 하네스 버그를 의심하고 턴별로 다시 찍어봤다.

```
턴1 "본다 온프레미스 이전 얘기 해줘"
  기존 → 검색 2회, 정답
  신규 → 검색 2회, 정답

턴2 "그때 인증이 왜 문제가 됐던 거야?"
  기존 → 검색 0회 → "포트폴리오에 아직 정리되어 있지 않습니다"
  신규 → 검색 1회 (질의: "온프레미스 이전 인증 BaaS JWT") → 정답
```

하네스 문제가 아니었다. 기존 모델은 후속 질문에서 **검색 도구를 아예 부르지 않고** 바로 모른다고 답했다. 첫 턴은 잘 답했는데도 그랬다.

나머지 실패도 같은 결이다. "역압은 왜 필요했나" 질문에서 기존 모델은 검색을 두 번 하고도 *"검색 결과에 역압이라는 용어의 직접적 설명이 없습니다"*라며 포기했다. 노트에 그 단어가 그대로 있는데도.

## 공짜는 아니었다

| 지표 | 기존 | 신규 |
|---|---|---|
| 지연 중앙값 | 6.4초 | 9.6초 |
| 지연 p90 | 9.5초 | 17.6초 |
| 출력 토큰 중앙값 | 205 | 499 |
| 답변 길이 중앙값 | 118자 | 868자 |
| 검색 호출 합 | 39회 | 56회 |

새 모델은 **1.5배 느리고 2.5배 비싸다.** 답변 길이는 7배가 됐는데, 이건 품질이라기보다 취향에 가깝다.

그래서 바꾸는 게 맞나. 이 계산을 어떻게 했냐면, **어떤 실패가 사용자에게 더 치명적인지**로 갈랐다. 3초 더 기다리는 건 불편이고, 후속 질문에 "정리되어 있지 않습니다"가 나오는 건 **대화가 끊기는 것**이다. 방문자가 꼬리 질문을 던지는 건 이 챗봇의 예외가 아니라 기본 사용 패턴이다.

그리고 바꾸는 김에 알게 된 게 하나 더 있다. 기존 모델 ID가 **공급자의 모델 목록에서 이미 내려가 있었다.** 호출은 되지만 언제 끊길지 모르는 상태로 프로덕션이 돌고 있었다는 뜻이다.

## 옮기고 나서 바로 터졌다

교체는 열 줄이면 끝날 줄 알았는데, 첫 요청부터 400이 났다.

```
function_response.name: Name cannot be empty
```

도구 실행 결과를 모델에 되돌려줄 때 함수 이름이 빈 채로 전송되고 있었다. 재밌는 건 **실험에서는 이 버그가 안 나왔다**는 점이다. 실험 하네스는 응답을 한 번에 받는 방식이었고, 프로덕션은 스트리밍이라 경로가 달랐다. 라이브러리 버전 조합에서 스트리밍 쪽 변환만 어긋나 있었다.

실험은 모델을 골라주지만 **통합까지 검증해주지는 않는다.** 하네스를 프로덕션과 최대한 같게 맞췄다고 생각했는데도 스트리밍이라는 축 하나가 빠져 있었고, 정확히 거기서 터졌다.

## 돌이켜보면

바꿀지 말지보다 **무엇을 재야 하는지**를 정하는 데 시간이 더 걸렸다. 그리고 그게 맞는 순서였다.

벤치마크 점수는 "어느 모델이 더 똑똑한가"에 답한다. 하지만 실제로 필요했던 답은 **"내 사용자가 겪을 실패가 어느 쪽이 적은가"**였고, 그건 내 시스템 프롬프트와 내 문서와 내 질문 분포 위에서만 잴 수 있다.

케이스 12개짜리 작은 실험이었고, 멀티턴 말고 다른 차이는 표본을 늘리면 흔들릴 수 있다. 그래도 **하네스를 만들어둔 게 남았다.** 다음에 또 새 모델이 나오면 이번엔 하루가 아니라 한 시간이면 답을 낼 수 있다.
